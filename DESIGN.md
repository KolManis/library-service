# Library Service — дизайн

Сервис библиотеки на Go в гексагональной архитектуре. Учебный проект с двумя целями:
Go-код и собственная тестовая инфраструктура (testcontainers, фикстуры, CI).

Документ живой: решения дописываются по мере принятия. Формат решений — «что решили,
почему, что отвергли».

---

## 1. Домен

Библиотека. Ограниченное число экземпляров книги, бронь на 3 дня, выдача на 14 дней,
воркеры снимают просрочку, штрафы за невозврат.

### Сущности

| Сущность | Поля | Что это |
|---|---|---|
| Book | id, title, author, isbn | Книга как издание |
| Copy | id, book_id, decommissioned | Физический экземпляр — ограниченный ресурс |
| Reader | id, full_name, email, status | Читатель |
| Loan | id, copy_id, reader_id, status, reserved_at, issued_at, due_at, returned_at | Выдача: от брони до возврата |
| Fine | id, loan_id, amount, status (pending/paid) | Штраф за просрочку |

### Машина статусов Loan

```
reserved ──issue──> issued ──return──> returned   (терминальный)
    │                  │
  expire           markOverdue
    │                  │
    v                  v
 expired           overdue ──return──> returned
(терминальный)
```

Правила:

- `reserved → issued | expired`
- `issued → returned | overdue`
- `overdue → returned` — просроченную книгу можно вернуть
- `returned`, `expired` — терминальные, из них переходов нет

Константы домена: бронь живёт **3 дня** (`ReservationTTL`), выдача — **14 дней**
(`LoanPeriodDays`). При возврате из `overdue` создаётся `Fine`.

## 2. Ключевые решения

### 2.1 Кто владеет фактом «экземпляр занят» — Loan, не Copy

**Решение.** У `Copy` нет статусов `available/reserved/issued` — только флаг
`decommissioned`. «Экземпляр свободен» — вычисляемый факт: нет активной Loan
(`reserved` или `issued`) на этот `copy_id`.

**Почему.** `reserved/issued` — состояние процесса выдачи, а не свойство физического
экземпляра. Хранение его в Copy — проекция состояния Loan на чужую сущность: два
UPDATE в двух таблицах на каждый переход, и любой сбой между ними даёт рассинхрон
(`loan = returned`, `copy = issued`) — экземпляр навсегда «занят». `decommissioned` —
свойство самого экземпляра (физически списали), поэтому остаётся.

Общий принцип: производные факты не храним как первичные данные. Если когда-нибудь
понадобится материализация ради производительности — это осознанный кэш со стратегией
пересчёта, а не «ещё одна колонка-правда».

**Отвергнуто.** Статус у Copy (вариант из первоначального брифа): быстрее запрос
свободных, но межтабличный инвариант нельзя выразить constraint'ом, и появляется
рассинхрон по конструкции.

### 2.2 Инвариант единственной активной выдачи — частичный уникальный индекс

**Решение.** Инвариант «не больше одной активной выдачи на экземпляр» обеспечивает
Postgres:

```sql
CREATE UNIQUE INDEX uniq_active_loan_per_copy
    ON loans (copy_id)
    WHERE status IN ('reserved', 'issued');
```

**Почему.** Это перевод инварианта из «разработчик не забыл FOR UPDATE» в «база
физически не даст». При гонке вторая транзакция получает unique violation независимо
от качества кода.

**Важно: индекс не отменяет код, а меняет его роль.** `SELECT свободного` + `INSERT`
остаётся TOCTOU-гонкой: обе транзакции видят экземпляр свободным, обе вставляют, одна
ловит ошибку. Приложение обязано обработать SQLSTATE `23505`: взять следующий
свободный экземпляр или вернуть 409. Код теперь про обработку отказа, а не про
поддержание инварианта.

**План упражнения (этап 3).** Индекс сознательно НЕ добавляется до этапа 3. Сначала
тест на гонку (N горутин на 1 экземпляр) воспроизводит овербукинг — красный. Потом
миграция с индексом + обработка 23505 — зелёный. Откат миграции — снова красный
(проверка честности теста).

### 2.3 Домен чистый, время — параметром

- Поля агрегатов приватные; изменение состояния — только через методы, методы
  сверяются с таблицей переходов. Невалидный объект не может существовать:
  единственная дверь — конструктор.
- Никаких gorm/json-тегов на доменных структурах. Персистентная модель — отдельная
  структура в `adapters/out/repositories` с маппингом. Это цена чистоты домена.
- Время всегда приходит параметром (`Issue(now time.Time)`), внутри домена нет
  `time.Now()`. Следствие: «время прошло» в тестах моделируется данными
  (`reserved_at = now - 4 дня`), никаких `Sleep`.
- Домен защищает инварианты сам: `Expire` проверяет, что бронь старше TTL,
  `MarkOverdue` — что срок прошёл. Правило не держится на вежливости воркера.
- Ошибки — sentinel-переменные (`ErrInvalidTransition`, `ErrNotYetDue`), проверка
  через `errors.Is`. Внешний код различает «нарушено бизнес-правило» (→ 409) и
  «инфраструктура упала» (→ 500) без сравнения строк.

### 2.4 События — через outbox

Доменные события (`LoanChanged`, `FineCreated`) агрегат копит в себе, наружу их
публикует не домен. Запись события в outbox-таблицу происходит в одной транзакции с
изменением агрегата; отдельный воркер (`cmd/outbox`) публикует их в Kafka. Гарантия:
не бывает «статус поменяли, событие потеряли».

### 2.5 Fine создаёт application-слой, не домен Loan

**Решение.** Правило «при возврате из overdue создаётся штраф» реализует команда
`return-loan`, а не метод `Loan.Return()`. Сценарий хендлера: запомнить статус до
возврата → вызвать `l.Return(now)` → если статус был `overdue`, создать `Fine` через
`IFineRepository` — обе записи в одной транзакции. Аналогично воркер штрафов: команда
`create-fines` координирует `Loan.MarkOverdue()` и создание `Fine`.

**Почему.** `Loan` и `Fine` — разные агрегаты. Если `Return()` начнёт создавать
`Fine`, домен loan узнает о чужом агрегате, граница сотрётся, и появится вопрос «а
кто его сохранит?» — домен репозиториев не видит. Координация нескольких агрегатов —
ровно то, для чего существует application-слой (см. роли слоёв, раздел 3).

**Отвергнуто.** Создание Fine внутри `Loan.Return()`: связывает агрегаты и требует
от домена знать о персистентности. Доменное событие `LoanReturned` с подпиской —
честная альтернатива, но для синхронного правила «возврат ⇒ штраф» это лишний
уровень косвенности; события оставляем для интеграции наружу (см. 2.4).

### 2.6 Расчёт суммы штрафа — за каждый день просрочки, округление вверх

**Решение.** `amount = FineRatePerDay * days`, где `days` — количество дней между
`due_at` и моментом возврата (`returnedAt`), округлённое вверх (неполные сутки
просрочки считаются целым днём). `FineRatePerDay` — константа домена в пакете
`fine`, по аналогии с `ReservationTTL`/`LoanPeriodDays` в пакете `loan`. Формулу
считает сам домен `Fine` (конструктор принимает `dueAt`/`returnedAt`, а не готовую
сумму) — это его собственное бизнес-правило, а не решение application-слоя.

**Почему.** Соразмерно проступку (день в день — не то же самое, что месяц), проще
фиксированной суммы объяснить читателю. Округление вверх — типичная практика для
штрафов («любая часть суток — штраф за сутки»), проще округления вниз в реализации
и не даёт читателю «бесплатных» часов задержки.

**Открыто.** Конкретное значение `FineRatePerDay` — заглушка на старте, тюнится
без изменения архитектуры.

## 3. Архитектура

Гексагон. Единственное настоящее правило — **зависимости (импорты) направлены только
внутрь**: `adapters → application → domain`. Домен не импортирует ничего, кроме
stdlib и uuid. Проверяется компилятором и ревью, папки — лишь отражение правила.

```
cmd/
  api/                      — HTTP-сервер
  book-consumer/            — Kafka-консьюмер
  expire-worker/            — воркер снятия броней
  fines-worker/             — воркер штрафов
  outbox/                   — публикация событий из outbox
internal/
  core/
    domain/
      aggregates/
        loan/               — агрегат: сущность + машина статусов + события
        book/  copy/  reader/  fine/
        shared-kernel/      — общие value objects
      services/             — доменные сервисы
    ports/                  — ИНТЕРФЕЙСЫ: ILoanRepository, ILoanChangedProducer…
    application/
      commands/             — папка на команду: command.go (DTO+валидация)
                              + command_handler.go (оркестрация)
      queries/              — get-reader-loans/
      domain-event-handlers/
  adapters/
    in/
      http/                 — echo-хендлеры
      consumers/            — Kafka-консьюмеры
      workers/              — воркеры по таймеру
    out/
      repositories/         — реализация портов на gorm+postgres
      producers/            — Kafka-продюсеры (protobuf)
      metrics/
api/
  events/*.proto            — контракты событий
migrations/                 — goose-миграции
test/
  integration/              — testcontainers
    fixtures/               — YAML-фикстуры
```

### Роли слоёв

- **domain** — правила, верные независимо от технологий (переходы, сроки, штрафы).
  Тестируется голым `go test` без Docker.
- **ports** — интерфейсы, объявленные внутри ядра, реализованные снаружи (инверсия
  зависимостей). В тестах вместо Postgres подставляется фейк.
- **application/commands** — оркестрация без бизнес-правил: достань → вызови домен →
  сохрани → опубликуй. Один и тот же хендлер команды дёргают HTTP, консьюмер, воркер
  и тест — напрямую.
- **adapters/in** — переводчики: HTTP/protobuf/тик таймера → команда → результат →
  HTTP-код/ack. Command bus не используется — адаптер держит конкретный хендлер.
- **adapters/out** — реализации портов: SQL, маппинг, обработка 23505, sarama.

### Путь запроса `POST /loans/{id}/issue`

1. echo-хендлер парсит id → `issueloan.Command`;
2. хендлер команды берёт агрегат у `ILoanRepository`;
3. за интерфейсом — Postgres-репозиторий: SELECT → сборка `loan.Loan`;
4. команда вызывает `l.Issue(now)` — домен проверяет переход, ставит `due_at`,
   поднимает `LoanChanged`;
5. `Save`: UPDATE + запись события в outbox одной транзакцией;
6. хендлер переводит `nil → 200`, `ErrInvalidTransition → 409`.

## 4. API

| Метод | Путь | Что делает |
|---|---|---|
| POST | /books/{id}/reserve | Забронировать свободный экземпляр (TTL 3 дня). Гонка за последний экземпляр — ровно один победитель |
| POST | /loans/{id}/issue | Выдать на руки, `due_at = now + 14 дней` |
| POST | /loans/{id}/return | Вернуть; из overdue — создаётся Fine |
| GET | /readers/{id}/loans | Выдачи читателя |

Фоновые процессы:

- воркер `expire-reservations`: `reserved` старше 3 дней → `expired`;
- воркер `overdue-fines`: `issued` с `due_at` в прошлом → `overdue` + `Fine`;
- консьюмер `book.decommissioned`: все экземпляры книги → `decommissioned`, активные
  брони отменяются;
- продюсер: `loan.changed` на каждую смену статуса, `fine.created`.

## 5. Схема БД (черновик — уточняется при написании миграций)

```sql
CREATE TABLE books (
    id      uuid PRIMARY KEY,
    title   text NOT NULL,
    author  text NOT NULL,
    isbn    text NOT NULL
);

CREATE TABLE copies (
    id             uuid PRIMARY KEY,
    book_id        uuid NOT NULL REFERENCES books (id),
    decommissioned boolean NOT NULL DEFAULT false
);

CREATE TABLE readers (
    id        uuid PRIMARY KEY,
    full_name text NOT NULL,
    email     text NOT NULL,
    status    text NOT NULL
);

CREATE TABLE loans (
    id          uuid PRIMARY KEY,
    copy_id     uuid NOT NULL REFERENCES copies (id),
    reader_id   uuid NOT NULL REFERENCES readers (id),
    status      text NOT NULL,
    reserved_at timestamptz NOT NULL,
    issued_at   timestamptz,
    due_at      timestamptz,
    returned_at timestamptz
);

-- Этап 3, отдельной миграцией (см. решение 2.2):
-- CREATE UNIQUE INDEX uniq_active_loan_per_copy
--     ON loans (copy_id) WHERE status IN ('reserved', 'issued');

CREATE TABLE fines (
    id      uuid PRIMARY KEY,
    loan_id uuid NOT NULL REFERENCES loans (id),
    amount  numeric(10,2) NOT NULL,
    status  text NOT NULL
);

-- outbox — DDL уточним на этапе 4
```

Поиск свободного экземпляра:

```sql
SELECT c.* FROM copies c
WHERE c.book_id = $1
  AND NOT c.decommissioned
  AND NOT EXISTS (
      SELECT 1 FROM loans l
      WHERE l.copy_id = c.id AND l.status IN ('reserved', 'issued')
  )
LIMIT 1;
```

Индекс `loans(copy_id, status)` появится вместе с частичным уникальным — `NOT EXISTS`
по нему ходит нормально, преждевременно не оптимизируем.

## 6. Тесты

Пирамида ложится на слои гексагона:

1. **Unit — домен.** Табличные тесты переходов: из каждого статуса каждое действие,
   ожидание — успех или конкретная sentinel-ошибка через `errors.Is`. Проверка
   честности: сломай таблицу переходов — тест обязан покраснеть.

   Тестовые дублёры портов (`fakeLoanRepo` и т.п.) сейчас пишутся руками в каждом
   пакете команды — при двух-трёх интерфейсах это нагляднее генерируемых моков.
   Когда портов станет много (`IFineRepository`, `IReaderRepository`,
   `ILoanChangedProducer`...), сделать один проход: `mockery` + `//go:generate` над
   каждым портом → сгенерировать в `internal/core/ports/mocks/` → заменить ручные
   fake, убрать дублирование (`fakeLoanRepo` уже продублирован между `reservecopy` и
   `issueloan`). Прод-код это не затрагивает — только тестовые дублёры за теми же
   интерфейсами, риск низкий.
2. **Integration — адаптеры (testcontainers).** Реальные Postgres+Kafka из кода
   теста, goose-миграции на поднятой БД. Репозитории (реальный SQL), команды,
   консьюмер (событие → изменение в БД), продюсер (действие → событие в топике).
   YAML-фикстуры. Изоляция: truncate между тестами, свои consumer groups.
3. **Гонки.** N горутин на 1 свободный экземпляр: овербукинг воспроизводится до
   индекса, после фикса — ровно одна выдача, остальные получают внятный отказ, не 500.
4. **Воркеры.** Хендлер команды вызывается напрямую (детерминированно), «время
   прошло» — фикстурой, не Sleep.
5. **E2E.** HTTP → БД → событие в Kafka → консьюмер → смена статуса → итоговое
   событие.

На каждый push/PR: `golangci-lint` → unit → integration (`-tags=integration`,

1. **[в работе]** Скелет гексагона, домен Loan + unit-тесты, Postgres+goose,

   этапы 2–5.

## 11. Инфраструктурный бэклог (этап 6)

Не блокирует этапы 2–5, делается постепенно. Часть инфраструктуры уже угадана
заранее: папка `adapters/out/metrics` заведена, но пуста; `opentelemetry` уже в
зависимостях (`go.mod`) как indirect, но нигде не используется.

### Приоритет — сделать раньше, а не откладывать

Четыре пункта ниже дешевле закрыть сейчас, чем ретрофитить на выросшей
кодовой базе — задержка именно так и превращает «дёшево» в «дорого»:

1. **`.golangci.yml` явным файлом** — сейчас гоняется только дефолтный набор
   golangci-lint (`errcheck`, `gosimple`, `govet`, `ineffassign`, `staticcheck`,
   `unused`). Добавить: `errorlint` (ловит нарушения паттерна sentinel-ошибок +
   `errors.Is` из решения 2.3 — автоматически, не только на код-ревью), `contextcheck` (правильная
   прокидка `context.Context`, критично для `dbFromContext`/`ITransactor`),
   `sqlclosecheck`, `forbidigo` (запретить вызовы БД без `Context`).
2. **`slog` вместо `log`** — сейчас в проекте всего 5-6 вызовов `log.*`
   (весь `cmd/api/main.go`). Мигрировать сейчас — копейки; после появления
   воркеров/консьюмера/продюсера мест станет в разы больше. `forbidigo`-правило
   на голый `log.*` держит это инвариантом, не «договорённостью на словах».
3. **Graceful shutdown** — `context.Context` + `signal.NotifyContext` вместо
   `e.Logger.Fatal(e.Start(...))`. Маленькая, изолированная правка (только
   `main.go`), закрывает уже отмеченный ниже критичный риск.
4. **Единый error-mapping слой** — до того, как формат
   `map[string]string{"error": ...}` разрастётся из 4 хендлеров в 8+
   (`GRPC-001`, будущие Kafka-эндпоинты).

### Наблюдаемость

- Структурные логи (`slog`) с request-id/trace-id вместо `log.Printf`.
- Трейсинг через otel (раз уже в зависимостях): HTTP → команда → БД → Kafka.
- Метрики Prometheus в `adapters/out/metrics`: латентность хендлеров, размер
  outbox-очереди, лаг консьюмера.
- `/healthz` (liveness) и `/readyz` (readiness, с проверкой соединения к БД) — сейчас
  отсутствуют.

### Локальные UI-инструменты (docker-compose)

Поднимаются рядом с Postgres+Kafka, бесплатны в self-hosted варианте:

- **Kibana + Elasticsearch** — просмотр логов. ES прожорлив по памяти (от ~2GB heap
  даже в минимальной конфигурации) — держать в уме при поднятии на слабой машине.
- **Grafana** — дашборды поверх Prometheus-метрик из `adapters/out/metrics`.
- **Jaeger** — визуализация трейсов (otel уже в зависимостях, но трейсинг пока не
  подключен — см. «Наблюдаемость» выше).
- **Kafka UI** (provectus/kafka-ui или kafdrop) — посмотреть содержимое топиков
  (`loan.changed`, `fine.created`, `book.decommissioned`) и лаг консьюмеров без
  консольного `kafka-console-consumer`.

### Живучесть процесса

- Graceful shutdown по SIGTERM (сейчас `e.Logger.Fatal(e.Start(...))` — при `kill`
  соединения обрываются, in-flight запросы теряются).
- Таймауты на все внешние вызовы (context deadline на запросы к БД), лимиты пула
  соединений gorm (`SetMaxOpenConns` и т.п.) — сейчас не настроены.
- Идемпотентность Kafka-консьюмера `book.decommissioned`: at-least-once доставка
  означает дубли, нужен dedupe по ключу события.

### API-слой

- Унифицировать формат ошибок (сейчас каждый хендлер руками собирает
  `map[string]string{"error": ...}`) + middleware: request-id, recover.
- Аутентификация/авторизация — сейчас `POST /books/{id}/reserve` бронирует от имени
  любого `reader_id` без проверки, что вызывающий — этот читатель.
- OpenAPI-спека, пагинация для `GET /readers/{id}/loans`.

### Данные

- В схеме нет `created_at`/`updated_at` — нужны для отладки инцидентов в проде.
- Retry с backoff на транзиентные ошибки БД.

### Деплой

- `Dockerfile` (multi-stage) + `docker-compose.yml` для локального поднятия
  Postgres+Kafka одной командой.
- Миграции сейчас гоняются на старте `cmd/api` (см. комментарий в коде — осознанный
  компромисс пет-проекта). Довести до отдельной cmd-команды `migrate`.
- Публикация образа из CI в registry — предпосылка для подписания образов ниже,
  сейчас пайплайн ничего не собирает и никуда не пушит.

### CI/безопасность

- `govulncheck` в CI (сканирование уязвимостей зависимостей).
- Кэш Go-модулей в actions, если ещё не кэшируется.
- Подписание образов (`cosign`, Sigstore): keyless-подпись через OIDC GitHub Actions
  + `cosign verify` как отдельный шаг. Проверяет, что задеплоенный образ — точно тот,
  что собрал CI, а не подменённый между сборкой и запуском. Имеет смысл только после
  появления Dockerfile + пуша образа в registry (см. «Деплой» выше) — подписывать
  сейчас нечего.
- Kafka: `SASL_SCRAM` (аутентификация — клиент доказывает пароль без передачи его
  по сети) + `SASL_SSL` (шифрование канала) для любого **реально достижимого**
  брокера. Не нужно для `testcontainers-go/modules/kafka` в тестах — контейнер
  одноразовый, изолирован в Docker-сети, никто снаружи до него не достучится.
  Нужно с первого брокера, до которого можно дотянуться не из теста — не раньше
  `KAFKA-002`/реального деплоя.
- Секреты (`DATABASE_URL` и будущие): пока GitHub Actions Secrets хватает с запасом
  — один секрет, нет деплоя. Vault (или аналог) — только если появится реальная
  причина: несколько окружений, ротация, аудит доступа. Не раньше.

## 12. SDET-практика (расширение scope, вне ядра library-service)

Не про library-service как продукт — про то, чтобы на этом же репозитории
закрыть навыки, которых сам домен не требует, но которые нужны для роста в SDET.
Не блокирует этапы 1–6, делается в конце, когда есть работающий HTTP API
(и желательно Dockerfile/docker-compose из раздела 11 — часть пунктов ниже
тестирует сервис как чёрный ящик, им нужно, чтобы сервис можно было поднять
одной командой).

### Нагрузочное тестирование (k6)

Сценарии поверх уже существующего HTTP API (`reserve`/`issue`/`return`/
`get-reader-loans`):

- **Baseline** — обычная нагрузка, снять p95/p99 latency и error rate как точку
  отсчёта.
- **Spike на `/books/{id}/reserve`** — много виртуальных пользователей ломятся
  за один и тот же экземпляр одновременно. Это тот же сценарий, что и
  `RACE-001`, только через реальный HTTP, а не горутины в тесте — хорошая
  проверка, что частичный уникальный индекс держит инвариант и под нагрузкой,
  не только в unit/integration-тесте. **Делать после `RACE-001`**, иначе
  спайк просто законно наловит овербукинг, который ещё не пофиксен, и это не
  будет находкой.
- **Soak** — средняя нагрузка на продолжительное время, искать утечки
  (соединения к БД, память).

### UI-автоматизация

Честно: у library-service сейчас нет UI вообще — это чистый backend API. Чтобы
получить полноценную практику Playwright/Selenium именно на этом репозитории,
придётся сознательно раздвинуть scope: добавить минимальный веб-фронт
(отдельный стек, не Go — например, простой vanilla JS/HTML или маленькое
React-приложение: список книг, кнопка «забронировать», список своих броней).
Это не нужно самому library-service как продукту — исключительно площадка для
автоматизации. Альтернатива — не трогать этот репозиторий и тренировать
UI-автоматизацию на отдельном, не связанном с library-service мини-проекте;
это чище архитектурно, но не даёт «сквозного» опыта на одном домене, который
знаешь вдоль и поперёк.

Если делать здесь — Playwright, не Selenium: один инструмент закрывает и
UI, и API-тестирование (см. ниже), актуальнее в вакансиях.

### Тестирование на других стеках (чёрный ящик)

Все существующие тесты проекта — «изнутри» Go-кодовой базы (unit на домене,
integration через testcontainers). Отдельная, ценная для SDET практика —
тестировать API как чёрный ящик, снаружи, другим стеком, не трогая исходники:

- **Python: `pytest` + `requests`** (или `httpx`) — набор тестов, которые
  просто дёргают поднятый (например, через `docker-compose up`) сервис по HTTP
  и проверяют контракт: коды ответов, JSON-схему, доменные инварианты снаружи
  (нельзя забронировать несуществующую книгу, нельзя вернуть то, что не
  выдавали).
- **Postman/Newman** — та же идея, но декларативно, с прицелом на
  CI-интеграцию (`newman run collection.json` отдельным шагом в GitHub
  Actions) и на то, чтобы коллекцию могли использовать не-программисты
  (QA без кода).

### Что ещё стоит рассмотреть (без обязательства делать)

- **Contract testing (Pact)** — между продюсером `loan.changed`/`fine.created`
  и консьюмером `book.decommissioned` из этапа 4. Естественное продолжение
  Kafka-интеграции, отдельная и специфичная для event-driven систем SDET-тема.
- **Базовый security-скан** (OWASP ZAP baseline scan) поверх поднятого API —
  дёшево добавить, реальный сигнал.
- **Отчётность по тестам** (`gotestsum` + JUnit-формат вместо голого
  `go test`) — под интеграцию с тест-менеджмент тулами (Allure, TestRail),
  если когда-нибудь понадобится показывать отчёты не-технической аудитории.

### gRPC-ручка (демонстрация гексагона — второй адаптер к тому же хендлеру)

Не про продукт: HTTP уже покрывает весь API, gRPC тут не нужен бизнесу. Смысл —
показать, что application-хендлер не знает и не должен знать о транспорте:
один и тот же `getreaderloans.Handler` вызывается и из HTTP, и из gRPC.

- **Контракт** — `api/grpc/reader_loans.proto`, сервис `ReaderLoansService`,
  один RPC `GetReaderLoans(reader_id) -> repeated LoanView`. Генерируется тем
  же `buf`, что и Kafka-контракты из `KAFKA-002` — общий тулинг.
- **Ручка** — `GetReaderLoans`, зеркало `GET /readers/{id}/loans`. Read-only,
  без побочных эффектов, наименее рискованный кандидат для первой gRPC-ручки.
  Новый адаптер `internal/adapters/in/grpc/reader_loans_server.go`, ядро не
  трогаем вообще.
- **Процесс** — тот же `cmd/api`, отдельный порт (HTTP :8080, gRPC :9090),
  не отдельный бинарник.
- **Ошибки** — `codes.InvalidArgument`/`codes.Internal` вместо HTTP-кодов, тот
  же принцип маппинга доменных/валидационных ошибок, другой транспортный язык.
- **Тесты** — `google.golang.org/grpc/test/bufconn`: in-memory gRPC-сервер
  прямо в тесте, без сети и без Docker.

## 13. Возможное расширение: рекомендации книг (RAG, локальная модель)

Не в основном roadmap — после всего остального (этапы 1–6, SDET-практика,
`GRPC-001`). Мотивация не про продукт: показать, что архитектура выдерживает
принципиально новую возможность без переписывания ядра, и попрактиковаться в
актуальном направлении без затрат на хостинг — только локальная модель, без
внешних платных API и ключей.

**Почему архитектура это позволяет.** Порты уже отделяют ядро от конкретных
реализаций — Postgres спрятан за `ILoanRepository`, скоро Kafka спрячется за
портом продюсера. Движок рекомендаций — тот же приём: новые порты в ядре,
конкретная реализация (локальная модель) — в адаптере. Домен `Loan`/`Book`/`Fine`
не узнает, что RAG вообще существует.

**Предпосылки, без которых начинать бессмысленно:**
- Домен `Book` сейчас пустой для retrieval — только `id/title/author/isbn`.
  Нужны описание и жанр/теги, иначе эмбеддить нечего.
- `pgvector` — расширение Postgres для хранения векторов, не отдельный
  датастор, ложится в существующую инфраструктуру.
- Локальная модель — Ollama (эмбеддинги и генерация текста через один и тот же
  локальный HTTP-сервис).

**Архитектурный набросок (когда дойдём):**
- Порты в ядре, разделены по одной ответственности (как остальные порты
  проекта): `IEmbedder` (текст → вектор), `IBookSimilaritySearch` (вектор →
  кандидаты книг), `ITextGenerator` (промпт → текст рекомендации).
- Адаптер `adapters/out/ollama/` реализует все три поверх локального Ollama.
- Application-слой: query `recommendbooks`, тот же паттерн, что уже есть у
  `getreaderloans` — история выдач читателя → `IEmbedder`+
  `IBookSimilaritySearch` → опционально `ITextGenerator` для человекочитаемого
  текста.
- HTTP: `GET /readers/{id}/recommendations`.

**Осознанно откладываем.** Не начинаем, пока не закрыт основной roadmap —
иначе распыляемся между backend/SDET-инженерией и AI-инженерией одновременно,
а это разные области с разным темпом освоения.
