# ADR-0011. Единый error-mapping слой вместо ручного `map[string]string` на хендлер

**Статус:** принято

## Контекст

Изначально каждый из 4 HTTP-хендлеров сам решал, как превратить доменную
ошибку в HTTP-ответ — своя цепочка `errors.Is`/`switch` и свой
`map[string]string{"error": ...}`. С ростом числа хендлеров (позже —
`GRPC-001`, Kafka-эндпоинты) эта логика начала бы дублироваться и
расходиться по мере роста.

## Решение

Один общий файл `internal/adapters/in/httphandlers/errors.go`:
`errorMapping` — таблица `{err error; code int; msg string}`, и две функции —
`respondError(c, err)` (проходит по таблице через `errors.Is`, не нашла — 500)
и `respondBadRequest(c, msg)` (400 с заданным текстом, для ошибок валидации
входа). Все 4 хендлера вызывают только их.

## Альтернативы

**Продолжать ручные цепочки `errors.Is` в каждом хендлере.** Отклонено не
абстрактно, а по факту: именно этот паттерн уже дал реальный баг —
`reader_loans_handler.go` возвращал `400` через `respondBadRequest` на
**внутреннюю** ошибку (должно быть `500` через `respondError`) — найдено при
ревью. Централизация не убирает возможность ошибиться, но убирает
дублирование самой логики "какая ошибка → какой код" по N местам, где её
пришлось бы держать синхронной вручную.

**Глобальный `echo.HTTPErrorHandler`, инспектирующий тип ошибки.** Echo
поддерживает кастомизацию на этом уровне, но для текущего числа хендлеров (4)
это более тяжёлый механизм, чем нужен — табличный маппинг решает ту же
задачу проще и очевиднее читается.

## Последствия

- Новая доменная ошибка требует одной строки в `errorMapping`, а не правки N
  хендлеров.
- Незамапленная ошибка молча падает в `500` — безопасный дефолт (не течёт
  наружу сырой текст ошибки/неверный статус), но означает, что забытая
  строка в таблице не даёт явной ошибки компиляции — только неверный код в
  ответе, если её не заметили при ревью.
