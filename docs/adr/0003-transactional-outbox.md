# ADR-0003. Transactional outbox для доставки доменных событий

**Статус:** принято

## Контекст

После `reservecopy`/`issueloan`/`returnloan` другие системы должны узнать о
смене статуса `Loan` (например, будущий сервис уведомлений) — через событие
в Kafka (`loan.changed`, `fine.created`).

Наивный вариант — опубликовать событие в Kafka прямо в command-хендлере,
сразу после сохранения агрегата в БД.

## Решение

**Transactional outbox.** `Loan`/`Fine` копят события в себе (`PullEvents()`
после мутации), хендлер пишет их в таблицу `outbox` **в той же транзакции**
(`ITransactor.WithinTransaction`), что и `Update`/`Create` агрегата. Отдельный
процесс `cmd/outbox` (`Tick`/`Run`) поллит неопубликованные строки, публикует
в Kafka, помечает `published_at`.

```
TX: [ INSERT/UPDATE loans + INSERT outbox ]  COMMIT
                                    │
                cmd/outbox: SELECT WHERE published_at IS NULL
                                    │
                          Kafka Publish(topic, key=AggregateID, payload)
```

## Альтернативы

**Прямая публикация в Kafka внутри хендлера.** Отклонено: БД закоммитилась,
публикация в Kafka упала (сеть/брокер недоступен) — событие тихо потеряно
навсегда, снаружи никто не узнает о смене статуса. Обратный случай тоже
возможен: публикация прошла, а транзакция БД потом откатилась (ошибка
дальше по цепочке) — Kafka получит событие про то, чего на самом деле не
произошло.

**Двухфазный коммит (2PC) между Postgres и Kafka.** Технически существуют
протоколы распределённых транзакций, но Kafka не проектировался под
классический XA/2PC, и цена операционной сложности несоразмерна выигрышу для
проекта такого масштаба.

**Debezium/CDC (читать WAL Postgres, стримить изменения строк в Kafka).**
Легитимная production-практика, избавляет от необходимости писать свой
outbox-воркер руками. Отклонено осознанно: цель этого проекта — попрактиковать
и понять сам механизм паттерна вручную (учебный проект), плюс Debezium
добавляет ещё один инфраструктурный компонент (Kafka Connect) сверх того, что
оправдано на этом этапе.

## Последствия

- Доставка — **at-least-once**: если `Publish` прошёл, а `MarkPublished`
  упал (например, процесс убили между ними), при следующем тике событие
  опубликуется повторно. Консьюмеры обязаны быть идемпотентны — это уже
  заложено в acceptance criteria `KAFKA-003`.
- Появляется отдельный процесс, за которым нужно следить: растущее число
  неопубликованных строк в `outbox` — сигнал проблемы (кандидат в
  Prometheus-метрики, `INFRA-BACKLOG`).
- Атомарность подтверждена не только по коду, а тестом с форсированным сбоем
  (`test/integration/outbox_atomicity_test.go`): падение `Append` откатывает
  и запись агрегата тоже. Доставка до реального брокера подтверждена
  отдельным тестом (`test/integration/outbox_worker_test.go`) — событие
  реально читается из топика с верным ключом и protobuf-содержимым, не
  только "код похож на правильный".
- Очередь в БД имеет предел пропускной способности при росте нагрузки; для
  этого масштаба проекта это не проблема, но это тот же компромисс, что и в
  любом outbox поверх реляционной БД.
