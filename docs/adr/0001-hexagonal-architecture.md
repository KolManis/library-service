# ADR-0001. Гексагональная архитектура (порты и адаптеры)

**Статус:** принято

## Контекст

Проект с самого начала должен был поддержать больше одной точки входа: HTTP
API (`cmd/api`) и фоновый воркер публикации событий (`cmd/outbox`), а позже —
Kafka-консьюмер (`cmd/book-consumer`, `KAFKA-003`). Все три должны вызывать
одну и ту же бизнес-логику (например, отменить бронь при списании) без
копипаста.

Наивный вариант — бизнес-правила прямо в HTTP-хендлере (модели с
gorm-тегами, `if`/`switch` по статусам прямо в обработчике запроса). Это
самый быстрый путь для маленького CRUD, но ломается ровно в момент, когда
появляется второй вызывающий (воркер/консьюмер): либо копируешь логику, либо
хендлер становится единственным местом, откуда её вообще можно вызвать — а
воркер физически не проходит через HTTP.

## Решение

Порты и адаптеры (гексагональная архитектура):

```
internal/core/domain          — чистые агрегаты (Loan, Fine), без БД/HTTP
internal/core/ports           — интерфейсы (ICopyRepository, IOutboxReader...)
internal/core/application      — command/query-хендлеры: оркестрация без бизнес-правил
internal/adapters/in           — HTTP, консьюмеры — переводят транспорт в команду
internal/adapters/out          — gorm-репозитории, Kafka-продюсер — реализуют порты
```

Зависимости — только внутрь: `adapters` знает про `core`, `core` не знает
про `adapters`. Порт объявлен в ядре, реализован в адаптере — инверсия
зависимостей. Один и тот же `command_handler.go` вызывается и из HTTP-хендлера
(`cmd/api`), и напрямую из теста, и (для `decommissioncopy`) будет вызван из
будущего Kafka-консьюмера — без дублирования логики.

## Альтернативы

**"Толстые" модели + логика в HTTP-хендлере.** Разобрано выше — ломается,
как только появляется второй вызывающий, не проходящий через HTTP.

**Clean Architecture / Onion Architecture.** По сути та же идея (слои,
зависимости внутрь), другая терминология и чуть более строгие правила
(use case interactors, DTO на границах). Выбран именно гексагон, потому что
термины "порт"/"адаптер" напрямую совпадают с тем, что реально написано в
коде (`ICopyRepository` — порт, `CopyRepository` — адаптер) — понятнее для
обучения, чем менее прямое соответствие терминов Clean Architecture.

**Микросервисы вместо слоёв в одном репозитории.** Рассматривалось отдельно
(см. обсуждение monorepo vs микросервисы) — отклонено на текущем этапе:
`cmd/api`/`cmd/outbox` делят одну БД и один Go-модуль, то есть это модульный
монолит с несколькими entrypoint'ами, не микросервисы. Разделение на настоящие
сервисы имеет смысл только когда появится домен с собственными данными,
которому не нужен прямой доступ к `loans`/`copies` (кандидат — гипотетический
`Donation`, обсуждали отдельно).

## Последствия

- Лишняя косвенность для проекта такого размера: почти на каждый порт — один
  реальный адаптер, интерфейс ради одной реализации. Цена оправдана тем, что
  `reservecopy`/`issueloan`/`returnloan`/`decommissioncopy` уже вызываются из
  HTTP и напрямую из unit-тестов без дублирования.
- Плодятся ручные `fake<Port>` тест-дублёры — по одному набору на каждый
  `command_handler_test.go` (см. `docs/style.md`: `fake<PortName>`, не
  generic `fakeRepo`). Через сгенерированные моки (mockery/gomock) это можно
  было бы сократить, но ручные заглушки читаются прозрачнее для обучения —
  осознанный выбор, не забытая оптимизация.
- Новый адаптер (например, gRPC-обёртка того же `getreaderloans.Handler`,
  `GRPC-001`) не требует изменений в `core` — только новый файл в
  `adapters/in`.
