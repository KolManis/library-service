# ADR-0002. Loan, а не Copy, владеет фактом «экземпляр занят»

**Статус:** принято

## Контекст

Нужно уметь ответить на вопрос "свободен ли этот экземпляр книги для брони"
(`FindFreeCopyID`). Наивный вариант — завести на `copies` поле-статус
(`available`/`reserved`/`issued`) и обновлять его синхронно с изменением
статуса `Loan`.

## Решение

У `Copy` нет статуса `available`/`reserved`/`issued` — только флаг
`decommissioned` (физически списан или нет). «Экземпляр свободен» —
**вычисляемый** факт, не хранимое поле:

```sql
SELECT c.id FROM copies c
WHERE c.book_id = ?
  AND NOT c.decommissioned
  AND NOT EXISTS (
      SELECT 1 FROM loans l
      WHERE l.copy_id = c.id AND l.status IN ('reserved', 'issued')
  )
```

Источник истины — только `loans.status`. `Copy` знает только про себя
(списан физически или нет), ничего не знает про чужой агрегат `Loan`.

## Альтернативы

**Хранить статус на `copies`, обновлять синхронно со статусом `Loan`.**
Отклонено: это два `UPDATE` в двух разных таблицах на каждый переход
(`reserve`, `issue`, `return`...). Любой сбой между ними — `loan` обновился,
`copy` нет (или наоборот) — оставляет перманентный рассинхрон:
`loan.status = returned`, но `copy.status` всё ещё `issued`. Экземпляр
навсегда "занят", хотя книгу давно вернули.

**Тот же вариант, но оба `UPDATE` в одной транзакции.** Устраняет риск
рассинхрона, но не устраняет саму проблему: `copies.status` стал бы просто
кэшем данных, которые и так целиком выводятся из `loans`. Пришлось бы держать
два источника истины про один и тот же факт синхронными вечно — а
`FindFreeCopyID` всё равно обязан заглянуть в `loans`, чтобы проверить
`decommissioned` НЕ единственное условие (нужно исключить ещё и `issued`,
а не только `reserved`) — так что обращение к `loans` не убирается в любом
случае, просто добавляется лишняя денормализация без выигрыша.

## Последствия

- `FindFreeCopyID` — не плоский `WHERE status = 'available'`, а
  `NOT EXISTS`-подзапрос. Чуть дороже по чтению, но корректен по построению —
  рассинхрона между `Copy` и `Loan` не существует как класса багов, потому
  что нечему рассинхронизироваться: только одна таблица хранит факт.
- Списание одной копии (`COPY-001`) не требует отдельной синхронизации со
  статусом брони — списание это независимый флаг на `Copy`, а отмена брони
  (если она была `reserved`) — отдельное, явное действие
  (`ILoanRepository.FindReservedByCopyID` + `Loan.Cancel()`), не побочный
  эффект обновления `copies`.
