# ADR-0004. Партиционный уникальный индекс как контроль гонки за экземпляр

**Статус:** принято

## Контекст

`FindFreeCopyID` находит свободный экземпляр, дальше хендлер создаёт `Loan`
со статусом `reserved`. Между "нашли свободный" и "создали бронь" — окно
гонки: две параллельные горутины/запроса могут обе увидеть один и тот же
экземпляр свободным и обе успешно создать `Loan` на него. Овербукинг
воспроизведён вживую тестом на 100 горутин на 1 свободный экземпляр
(`test/integration/reserve_race_test.go`) **до** фикса — тест реально красный.

## Решение

Частичный уникальный индекс на уровне БД:

```sql
CREATE UNIQUE INDEX uniq_active_loan_per_copy
ON loans (copy_id) WHERE status IN ('reserved', 'issued');
```

Вторая параллельная вставка `Loan` на тот же `copy_id` со статусом
`reserved`/`issued` падает с `SQLSTATE 23505`. `LoanRepository.Create`
перехватывает эту ошибку через `errors.As(err, &pgErr)` (`*pgconn.PgError`)
и маппит на `ports.ErrConcurrentReservation` → HTTP 409 в
`reserve_handler.go`. Проигравшая горутина получает внятный отказ, а не
искажённые данные.

## Альтернативы

**Блокировка на уровне приложения (мьютекс в Go).** Отклонено: не работает
при нескольких процессах/репликах `cmd/api` — у каждого свой адрес памяти,
мьютекс в одном процессе не видит гонку из другого.

**`SELECT ... FOR UPDATE` на строку `Copy` вокруг всего сценария брони.**
Технически возможно, но инвазивнее: `Copy` не хранит статус (ADR-0002),
"свободна" — вычисляемый факт из `loans`, так что блокировать нечего одной
строкой — пришлось бы блокировать саму проверку `NOT EXISTS` на нужную
изоляцию транзакций, что сложнее и менее очевидно читается, чем именованный
constraint.

**Optimistic locking (колонка `version`).** Решает другую проблему —
конкурентную запись **в одну и ту же строку**. Тут проблема другая: два
**разных новых** `Loan`, ссылающихся на один `copy_id` — версионирование
одной строки этого не ловит, всё равно нужна была бы уникальность на уровне
БД для детекта конфликта.

**`SERIALIZABLE`-изоляция транзакций для всего сценария брони.** Тоже могло
бы предотвратить аномалию, но дороже (везде нужна retry-логика на serialization
failure) и не самодокументируется так, как именованный constraint — индекс
работает независимо от того, вспомнил ли разработчик обернуть код в нужный
уровень изоляции.

## Последствия

- Инвариант живёт **в БД**, а не только в коде приложения — даже баг в
  прикладной логике не может его нарушить, constraint сработает всегда.
- Приложение обязано явно обрабатывать `23505` — это не "ошибка сама
  разрулилась", а нужен явный маппинг (`ports.ErrConcurrentReservation`).
- Проверено воспроизводимым циклом, не только "тест зелёный один раз":
  красный без индекса → зелёный с индексом → снова красный после отката
  миграции — доказательство, что тест ловит именно эту проблему, а не
  что-то другое (см. `RACE-001` в `docs/feature_list.json`).
