# ADR-0010. CQRS: раздельные read/write порты на одной и той же таблице

**Статус:** принято

## Контекст

`getreaderloans`-запросу (`GET /readers/{id}/loans`) нужен только один метод
чтения (`FindByReaderID`), возвращающий плоские данные для отображения.
Командам (`reservecopy`/`issueloan`/`returnloan`) нужны совсем другие методы
(`Create`/`GetByID`/`Update`) над той же таблицей `loans`. Аналогично для
`outbox`: командные хендлеры только дописывают в неё (`Append`), а читает и
помечает опубликованным — только фоновый воркер (`FetchUnpublished`/
`MarkPublished`).

## Решение

Один и тот же адаптер (`LoanRepository`, `OutboxRepository`) реализует **два
разных порта** над одной таблицей:

- `ILoanRepository` (`Create`/`GetByID`/`Update`/`FindReservedByCopyID`) —
  для команд.
- `IReaderLoansReader` (`FindByReaderID(...) ([]LoanView, error)`) — для
  запроса. `LoanView` — плоская read-модель, не доменный агрегат `Loan`:
  запрос не восстанавливает полный объект с бизнес-правилами ради того,
  чтобы просто отдать данные наружу.
- `IOutboxRepository.Append` (пишет) отдельно от `IOutboxReader.FetchUnpublished`/
  `MarkPublished` (читает и помечает) — только `cmd/outbox` знает про второй
  порт, командные хендлеры про него не подозревают.

## Альтернативы

**Один "толстый" интерфейс репозитория со всеми методами сразу.** Отклонено:
нарушает Interface Segregation — вызывающий код вынужден зависеть от
методов, которые ему не нужны. Практическая цена уже видна в проекте:
`ILoanRepository` (write-порт) сам по себе **не** разбит по вызывающему коду
до конца — когда в нём появился `FindReservedByCopyID` (для `COPY-001`),
все три `fake<LoanRepo>` в `issueloan`/`reservecopy`/`returnloan` пришлось
доучить пустой заглушкой этого метода, хотя ни один из них его не
использует. Это ровно тот компромисс, которого read/write-разделение
избегает **между** чтением и записью, но не устраняет **внутри** самого
write-порта — сознательно не доведено до полного разделения "по методу на
интерфейс", это было бы избыточно для масштаба проекта.

**Полноценный CQRS с отдельной read-моделью/материализованным представлением
(отдельная таблица/view под запросы).** Рассмотрено и отклонено как
избыточное — здесь разделение только на уровне Go-интерфейсов, одна и та же
таблица и один и тот же struct-адаптер реализует оба порта. "CQRS для
бедных": разделение ответственности есть, разделения инфраструктуры нет.

## Последствия

- `getreaderloans`-хендлер зависит только от `IReaderLoansReader` — тестовый
  дублёр под него не обязан знать про `Create`/`Update`, которые ему
  никогда не понадобятся.
- Схема таблицы всё равно одна — при её изменении оба порта (write и read)
  нужно проверить на согласованность руками, автоматической защиты от
  рассинхрона между `loanModel`/`LoanView`/доменным `Loan` не существует.
