# Library Service — Agent Operating Guide

Харнесс для этого репозитория (по мотивам harness-engineering-guide): короткая
карта поведения агента + состояние между сессиями + проверяемое "готово" вместо
устных договорённостей в чате. Архитектурные решения, домен, API, схема БД,
тесты и roadmap по этапам — в [DESIGN.md](DESIGN.md), здесь не дублируется.

## Начало сессии

1. Прочитать `docs/progress.md` — что сделано в прошлой сессии, с чего продолжать.
2. Прочитать `docs/feature_list.json` — актуальные статусы фич.
3. Проверить `git status` и `git log --oneline -10` — не разошлось ли с тем, что
   написано в docs/progress.md и docs/feature_list.json. Источник истины —
   репозиторий; если файлы состояния разошлись с реальностью, сначала разобраться,
   почему, и поправить их, а не действовать по устаревшей записи.
4. Выбрать одну фичу со статусом `in_progress` (первым делом) или `planned` с
   наивысшим приоритетом. Не начинать несвязанную работу, пока текущая не закрыта
   или не оставлена с явным handoff в `progress.md`.
5. Если у фичи есть спека (`specs/NNN-фича/`) — прочитать `spec.md` и `tasks.md`
   перед кодом. Нет спеки — сначала написать её (см. ниже), потом код.

## Рабочие правила

- Одна фича за раз, маленькие проверяемые изменения.
- **Спека до кода** (ADR-0014): на новую фичу из `feature_list.json` сначала
  `specs/NNN-фича/spec.md` (что строим, поведение, граничные случаи) и
  `tasks.md` (шаги с чекбоксами), потом реализация. Мелкие правки внутри уже
  закрытой фичи спеки не требуют.
- **ADR до кода** — если решение имеет отвергнутые альтернативы, оно
  оформляется в `docs/adr/` до реализации, а не задним числом.
- Не помечать фичу `done` без верификации (см. ниже) — уверенность модели не
  доказательство.
- Не менять acceptance criteria в `docs/feature_list.json`, чтобы подогнать под
  незавершённую работу — только явным решением человека.
- Если заблокирован — зафиксировать блокер и последнее проверенное состояние в
  `docs/progress.md`, не оставлять код в неопределённом состоянии.
- Архитектурные правила, доменные инварианты — см. DESIGN.md; стиль кода
  (комментарии, импорты, нейминг) — см. [docs/style.md](docs/style.md). Не
  придумывать заново по ходу.

## Definition of done

- `go build ./...`, `go vet ./...`, `go test ./...` — зелёные.
- Если затронут integration-слой: `go test -tags=integration ./test/integration/...`
- `gofmt -l` чист (CRLF от Windows-редактора — не в счёт, `.gitattributes` с
  `eol=lf` нормализует при коммите, руками не чинить).
- Статус фичи в `docs/feature_list.json` обновлён, с указанием команды-доказательства.
- Если у фичи есть спека: все пункты `specs/NNN-фича/tasks.md` отмечены, а
  поведение совпадает со `spec.md` (разошлось — либо доделать, либо явно
  зафиксировать расхождение, а не молча оставить).
- `docs/progress.md` содержит запись сессии: что сделано, чем проверено, что
  осталось, с чего продолжать следующей сессии.

## Карта документов

| Файл | Что там |
|---|---|
| [DESIGN.md](DESIGN.md) | Домен, архитектура, API, схема БД, инварианты, roadmap по этапам, инфраструктурный бэклог |
| [docs/adr/](docs/adr/README.md) | Архитектурные решения: контекст, выбор, отвергнутые альтернативы, последствия — по одному на файл |
| `specs/NNN-фича/` | Спека фичи до кода: `spec.md` (что строим, поведение, граничные случаи) + `tasks.md` (шаги с чекбоксами). См. ADR-0014 |
| [docs/style.md](docs/style.md) | Стиль кода: комментарии, импорты, нейминг, перенос строк |
| [docs/feature_list.json](docs/feature_list.json) | Машиночитаемый статус фич: приоритет, acceptance criteria, команда проверки |
| [docs/progress.md](docs/progress.md) | Журнал сессий: что сделано, что проверено, handoff следующей сессии |
