# Спека: KAFKA-003 — консьюмер `book.decommissioned`

**Статус:** черновик, до реализации
**Связанные документы:** [ADR-0006](../../docs/adr/0006-book-vs-copy-decommission.md)
(почему книга и копия — разные сценарии), [ADR-0005](../../docs/adr/0005-loan-cancelled-only-from-reserved.md)
(почему отмена только из `reserved`), [ADR-0003](../../docs/adr/0003-transactional-outbox.md),
[ADR-0007](../../docs/adr/0007-testing-strategy.md)

## Зачем

Внешняя система каталога сняла книгу с оборота целиком (истекла лицензия на
издание, отзыв тиража, списание по акту). Наш сервис должен узнать об этом
асинхронно и привести своё состояние в соответствие: экземпляры этой книги
больше не выдаются, а те, кого она ждала в брони, должны получить отмену, а
не молча прийти за книгой, которой нет.

Продюсер события в этом проекте **не реализуется** — по контракту он живёт во
внешнем bounded context. В тестах его роль играет обычный `sarama`-продюсер.

## Контракт события

Топик: `book.decommissioned`
Ключ сообщения: `book_id` (строка) — сохраняет порядок событий об одной книге
Формат: protobuf, новый файл `api/events/v1/book_decommissioned.proto`

```protobuf
message BookDecommissioned {
  string book_id = 1;
  google.protobuf.Timestamp occurred_at = 2;
}
```

Причина списания в контракт **не входит**: на поведение нашего сервиса она не
влияет, а лишнее поле в чужом контракте — лишняя связанность.

## Поведение

### Основной сценарий

Пришло событие про книгу, у которой есть экземпляры, и на части из них —
активные брони.

1. Все `copies` этой книги получают `decommissioned = true`.
2. Все выдачи со статусом `reserved` на этих экземплярах переходят в
   `cancelled`, каждая поднимает `LoanChanged` в outbox.
3. Выдачи со статусом `issued` **не трогаются** — книга физически у читателя,
   он вернёт её штатным `Return` (ADR-0005). После возврата экземпляр просто
   перестаёт предлагаться в `FindFreeCopyID`, отдельного действия не нужно.
4. Всё перечисленное — **в одной транзакции**. Частичное применение
   недопустимо: списанные копии с живыми бронями на них — испорченное
   состояние.

### Книга неизвестна или у неё нет копий

Не ошибка. Каталог может списать книгу, которой у нас никогда не было в
фонде. Обработчик отрабатывает вхолостую, offset коммитится. Иначе одно
чужое событие блокировало бы партицию навсегда.

### Повторная доставка того же события

Не падает и не портит состояние. Идемпотентность здесь **естественная**, без
таблицы обработанных событий:

- `UPDATE copies SET decommissioned = true` повторно — no-op;
- `reserved`-броней на этих копиях после первого прохода уже нет, значит
  второй проход отменяет пустой список.

То есть `Loan.Cancel()` на втором проходе просто не вызывается, и
`ErrInvalidTransition` не возникает.

### Сообщение не декодируется

Битый protobuf — это запись, которая не заработает никогда, сколько ни
повторяй (та же природа, что у «отравленной» записи в `OUTBOX-001`).
Поведение: залогировать с телом сообщения и offset, **закоммитить offset** и
идти дальше. Не коммитить — значит заблокировать партицию навсегда одним
кривым сообщением.

Полноценный DLQ-топик (переложить сообщение и продолжить) — осознанно **вне
объёма** этой фичи: это отдельное решение с альтернативами, ему нужен свой
ADR. Здесь — минимально живучий вариант: не молчать и не блокировать.

## Границы — что НЕ делаем

- Не реализуем продюсера `book.decommissioned`.
- Не заводим DLQ-топик (см. выше).
- Не добавляем таблицу обработанных событий для дедупликации — идемпотентность
  достигается природой операции, а не журналом.
- Не трогаем `issued`-выдачи ни в каком виде.
- Не меняем HTTP API — у этой фичи нет синхронной ручки.

## Технические требования

**Транзакционность.** Списание копий + отмена броней + запись событий в
outbox — через `ports.ITransactor.WithinTransaction`, как в
`decommissioncopy`.

**Коммит offset — после успешной обработки**, не до. Доставка at-least-once:
падение между обработкой и коммитом приведёт к повторной доставке, что
безопасно (см. идемпотентность выше).

**Изоляция тестов.** Уникальные имя топика и consumer group на каждый тест
(`"book.decommissioned-" + uuid`). Причина конкретная: существующий
`outbox_worker_test.go` читает с `sarama.OffsetOldest`, и как только в сьюте
на общем брокере появится второй тест, он вычитает чужое сообщение вместо
своего. Не наступать на это в новом сьюте.

**Graceful shutdown.** Консьюмер останавливается по сигналу через общий
`infra.ShutdownContext()`; фоновая горутина `Consume` завершается по отмене
контекста, `ConsumerGroup.Close()` вызывается с проверкой ошибки.

## Что появится в коде

| Слой | Что |
|---|---|
| Контракт | `api/events/v1/book_decommissioned.proto` → `pkg/events/v1` |
| Порты | `ICopyRepository.DecommissionAllByBookID`, `ILoanRepository.FindReservedByBookID` |
| Адаптеры out | Реализация обоих методов в `copy_repository.go` / `loan_repository.go` (джойн `loans`↔`copies` по `copy_id`) |
| Application | Команда `decommissionbook` (`command.go`, `command_handler.go`) |
| Адаптеры in | `internal/adapters/in/consumers/book_decommissioned_consumer.go` — `sarama.ConsumerGroupHandler` |
| Точка входа | `cmd/book-consumer/main.go` на `internal/infra` + `internal/config` |
| Конфиг | `KAFKA_CONSUMER_GROUP` в `config.Load()` (дефолт — `library-service`) |

Домен не меняется вообще: `Loan.Cancel()` и `StatusCancelled` уже есть из
`COPY-001`.

## Критерии приёмки

1. Консьюмер декодирует protobuf `book.decommissioned` из реального топика.
2. Все `Copy` книги получают `decommissioned = true`.
3. Все `reserved`-брони на этих копиях переходят в `cancelled`, события
   `LoanChanged` лежат в `outbox`.
4. `issued`-бронь остаётся нетронутой — статус не изменился, события нет.
5. Повторная доставка того же сообщения не падает и не меняет состояние
   повторно.
6. Событие про неизвестную книгу обрабатывается вхолостую, без ошибки.
7. Сбой внутри обработки не оставляет частичного состояния (проверка отката
   транзакции по образцу `outbox_atomicity_test.go`).
8. Интеграционный тест использует уникальные топик и consumer group.

Проверка: `go test -tags=integration ./test/integration/... -run TestBookConsumerSuite`

## Открытые вопросы

- **Размер батча и порядок.** События об одной книге упорядочены ключом, но
  если каталог пришлёт списание двух разных книг одновременно, они лягут в
  разные партиции и обработаются параллельно. Для текущего домена это
  безопасно (книги независимы), но стоит зафиксировать явно, если появится
  межкнижная логика.
- **Нужен ли отдельный `cmd/book-consumer` или консьюмер стоит поднимать
  внутри `cmd/api`.** Пока выбран отдельный процесс — так же, как `cmd/outbox`,
  и так же он сможет масштабироваться независимо. Если окажется, что плодить
  бинарники неудобно, это кандидат на объединение через Cobra-подкоманды
  (обсуждали, в бэклоге `DESIGN.md` §11).
